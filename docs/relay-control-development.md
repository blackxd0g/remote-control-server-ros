# REL-02: локальный прототип защищённого управления

Разработка 2026-09-07. Публикация в GitHub/Docker Hub и установка в production запрещены пользователем. Версия опубликованного сервера/relay остаётся 2.2.1; новые функции доступны только из текущих локальных исходников и dev-сборок.

## Контракт

| Endpoint | Авторизация | Назначение |
|---|---|---|
| POST /api/admin/relay-servers/{id}/enrollment | Пользователь с relays.write | Выдать одноразовый код на 10 минут; аннулировать старый credential |
| DELETE /api/admin/relay-servers/{id}/credential | Пользователь с relays.write | Отозвать код/credential и закрыть control-канал |
| POST /api/relay/enroll | HTTPS + relay_id/enrollment_token в JSON | Однократно обменять код на индивидуальный credential |
| GET /api/relay/{id}/control | WSS + Authorization: Bearer credential | Постоянный исходящий control-канал relay |
| GET /internal/v1/relay/select | Центральный internal token, не публикуется | Выбрать healthy relay с готовым управляющим каналом |
| POST /internal/v1/relay/permit | Центральный internal token, не публикуется | Установить permit и дождаться подтверждения WSS-узла |

Создание одноразового кода в консоли является одобрением конкретного relay администратором. Самостоятельная регистрация неизвестных relay не разрешена. Raw credential возвращается однократно и хранится на узле в JSON-файле; в БД сохраняется SHA-256 verifier. Новый credential не принимается в пользовательских/административных API или как internal token.

Ряд `relay_credentials` сохраняется после отзыва: gateway не переключает такой узел обратно на UDP. При удалении relay ряд удаляется каскадно. Передачу кода и ответа enrollment выполнять через HTTPS; response имеет Cache-Control: no-store. При потере ответа нужно выпустить новый код.

`RDS_HBBS_RELAY_CONTROL_MODE=gateway` — режим HBBS по умолчанию в новой локальной реализации. Он выбирает relay через центральный API и выдаёт клиенту адрес после успешного permit. Значение `legacy` явно включает прежний прямой UDP и предназначено только для старых узлов в доверенной сети. Новый API также умеет передавать UDP permit старым relay, у которых никогда не было ряда credentials. Выбор между WSS и legacy выполняется по серверной БД, не по присланному клиентом флагу.

На отдельном HBBR задаются `RDS_RELAY_CONTROL_MODE=wss`, `RDS_RELAY_CONTROL_URL=wss://server.example/api/relay/ID/control` и `RDS_RELAY_CREDENTIAL_FILE=/run/secrets/relay.json`. HBBR не читает internal.secret и не слушает управляющий UDP в этом режиме. `legacy` остаётся отдельным режимом совместимости HBBR.

## Протокол и границы

Актуальное дополнение: [постоянная доставка lifecycle](relay-durable-delivery.md) заменяет прежнюю очередь в пределах сессии. Старые ограничения очереди ниже относятся к предыдущему этапу и не описывают новый durable-режим.

- Сервер посылает hello с новым session UUID; relay очищает старые неиспользованные permits/ожидающие пары и отвечает ready. До ready команды не отправляются.
- Команда содержит type=command, session, request_id, uuid, action=permit/terminate, expires_at (Unix milliseconds). Требуется синхронизированное системное время. Разрешение на пару действует 30 секунд и допускает два подключения.
- Ответ ack должен совпасть по session, request ID и UUID. Сервер ждёт подтверждения не более 3 секунд. Повтор request ID возвращает прежний результат, не восстанавливая использования permit. Другой payload с тем же ID запрещён.
- WSS-клиент проверяет hostname/CA/срок сертификата; SSL_CERT_FILE позволяет использовать собственный доверенный CA без отключения проверки. Ограничены размер control-сообщения (8 KiB), скорость сообщений, число ожидающих команд и permits. В data handshake добавлены таймауты; переходы permit/pair/terminate защищены общим mutex.
- Отзыв/ротация через эту API-ноду закрывают канал сразу. Проверка credential и состояния relay повторяется при каждой команде и heartbeat. Для multi-API ещё нужны общая доставка команд/инвалидация; текущий gateway имеет процессную область действия.
- При потере управления существующие data-пары не обрываются. Неиспользованные permits и ожидающие пары очищаются после обнаружения разрыва. Terminate при недоступном канале не объявляется успешным.
- Reverse proxy должен перезаписывать X-Forwarded-Proto и быть явно перечислен в RDS_TRUSTED_PROXIES. Заголовок от недоверенного peer удаляется. Backend API не следует публиковать в обход proxy; /internal/v1/* не является публичным relay API.

## Проверки и остаток

Автоматические тесты покрывают конкурентное использование enrollment (только один успешный обмен), expiry/отзыв, отказ чужому relay ID, недоверенный proxy header, невозможность прочитать internal snapshot/admin API relay-ключом, ожидание и корреляцию ack, закрытие и запрет reconnect после отзыва.

`TestRelayBinaryWSS` запускает настоящий локальный Rust HBBR с тестовым TLS API: сначала недоверенный CA, затем доверенная цепочка; TCP/WS/mixed данные, отсутствие общего секрета, занятый legacy UDP-порт, принудительное завершение из API и сохранение активной пары при отзыве управляющего ключа. Для запуска указать `RDS_TEST_HBBR_BINARY` — без него тест явно пропускается.

Пример из Linux-контейнера, в который смонтирован проект:

```sh
cd art-api
RDS_TEST_HBBR_BINARY=/src/work/rel02/art-hbbr go test -v ./internal/httpapi -run 'TestRelay(BinaryWSS|SecureControl)' -count=1
```

## Предыдущий этап устойчивости — 2026-09-07, локально

- Команда повторяется каждые 750 мс в пределах исходного трёхсекундного ожидания. Session/request ID/UUID/action/deadline не меняются: повтор возвращает кешированный ответ и не восстанавливает permit. При disconnect ожидающая команда завершается с ошибкой доступности.
- До ready gateway не принимает telemetry/lifecycle/ack; готовность должна быть заявлена за 5 секунд. Повторный ready отклоняется. Обработчик report получает контекст с таймаутом 3 секунды; это требует соблюдения контекста самим хранилищем.
- Новые lifecycle-сообщения содержат request_id. API отвечает lifecycle_ack с теми же session/request ID/UUID/status только после успешного report. Повтор того же события подтверждается без повторного report, включая повтор closed; другой payload с тем же ID закрывает канал. В одной control-сессии хранится до 8192 подтверждённых событий, затем канал закрывается для ограничения памяти.
- HBBR сохраняет порядок active/closed в очереди до 1024 неподтверждённых сообщений; отправляет следующее после ack, потерянный ack вызывает повтор через 750 мс. Очередь producer также ограничена; при длительной перегрузке события ещё могут теряться. Это не durable outbox и не гарантия exactly-once через сбои процесса.
- При reconnect используется equal jitter: задержки 0.5–1, 1–2, 2–4, 4–8, 8–16, затем 15–30 секунд. После сессии длительностью от 60 секунд счётчик сбрасывается. Существующие data-пары сохраняются; старые permits не переносятся.
- Очередь событий и дедупликация имеют область одной control-сессии. При разрыве/перезапуске неподтверждённые события не восстанавливаются; отчёты старых активных пар не переавторизуются. Durable journal, восстановление авторизации событий и межузловая доставка остаются открытыми.
- Обновлять локальные API и HBBR совместно. Старый HBBR может присылать lifecycle без request_id, но для таких сообщений новый ack/dedup не предоставляется. Старый API не подтверждает события нового HBBR.

Проверены 6 gateway regression tests (потеря ack, неизменность retry, disconnect, lifecycle dedup/подмена, ошибка storage, ready/timeout/reconnect), 31 Rust unit test, полный Go test/vet, Rust fmt/clippy и настоящий amd64 HBBR на TLS-стенде. Точные результаты — в [журнале](journal/2026-09-07.md). UI не менялся и повторно не собирался.

Durable delivery реализована следующим локальным блоком: [контракт](relay-durable-delivery.md). Перед будущим релизом остаются нагрузка, retention/разбор очереди при ротации, PostgreSQL runtime, multi-API маршрутизация или явное ограничение одного API, публичный HTTPS стенд, официальный клиент и ARM64. REL-02 целиком не принят.
