# REL-OPS-02: обслуживание карантина и локальная надёжность

Локальная разработка 2026-09-07, продолжение [REL-OPS-01](relay-operations.md). API и HBBR обновляются совместно. Публикации и установки нет.

## Действия администратора

1. В разделе relay открыть «Очередь и история», затем «Открыть / обновить список» в обслуживании карантина. Страницы содержат до 10 событий; показывается общее количество. Для чтения требуется `relays.read`.
2. С правом `relays.write` скачать полный JSON. Все страницы должны принадлежать одной ревизии. При изменении карантина экспорт отклоняется целиком; обновить список и повторить. В JSON нет credential, но есть идентификаторы соединений: хранить в защищённом месте, не прикладывать к общедоступным журналам.
3. Убедиться, что файл сохранён, затем подтвердить «Архивировать и освободить очередь». В интерфейсе действие доступно после экспорта этой ревизии. API дополнительно требует точную ревизию и `confirm: true`; серверная резервная копия обязательна независимо от браузерного экспорта.

Relay создаёт `quarantine-<revision>.json` на своём outbox-томе с правами 0600 на Unix, без перезаписи существующего файла, и выполняет fsync файла/каталога. Только затем он очищает подтверждённый карантин и сохраняет новый outbox snapshot. Неполная/несовпадающая резервная копия блокирует очистку. Pending-события и активные соединения не удаляются, старые события не применяются к новой генерации ключа.

Изменение карантина после просмотра отменяет действие по прежней ревизии. Повтор последней успешно записанной ревизии после потери ответа или restart подтверждает прежнюю операцию и не удаляет новые события. Для более старых операций возвращается конфликт. При потере ответа результат может быть неизвестен: обновить список, проверить резервный файл и аудит; не подменять ревизию автоматически.

## API и аудит

- GET `/api/admin/relay-servers/{relayID}/quarantine?revision=...&offset=...`: `relays.read`, первая страница допускает пустую ревизию.
- GET `/api/admin/relay-servers/{relayID}/quarantine/export?revision=...`: `relays.write`, JSON только после получения полного согласованного снимка. До 4096 событий, deadline 60 секунд, bounded WSS-страницы.
- POST `/api/admin/relay-servers/{relayID}/quarantine/archive`: `relays.write`, JSON с `revision` и `confirm: true`. Команда не отправляется, если обязательное сохранение намерения в аудит не удалось.

Экспорт и архивирование записывают намерение и результат в runtime-аудит приложения. У архивирования есть operation ID. HTTP/API-аудит и fsync удалённого relay не образуют общую транзакцию: при сбое итог может быть `unknown`, при ошибке записи результата сохраняется предварительное намерение. Успех не заявляется без ответа relay. Ответы имеют Cache-Control: no-store. Чтение постраничного списка не создаёт отдельную запись аудита на каждую страницу.

## Восстановление и хранение

Snapshot остаётся версии 2, добавлены ревизия карантина и последняя архивированная ревизия; отсутствующие поля прежнего локального v2 инициализируются при открытии. Не откатывать на бинарник без поддержки этих полей: он не сохраняет гарантии повторного архивирования. Перед обновлением сохранять согласованную резервную копию тома при остановленном relay.

При отказе записи после резервирования может остаться прежний outbox и уже готовый архив. После восстановления диска и restart relay читает прежний snapshot; повтор с его ревизией проверяет совпадение существующего архива и завершает операцию. Это проверено тестом. Не удалять конфликтующий архив автоматически: сохранить копии и исследовать причину.

Архивные файлы не входят в лимит активной очереди, но занимают диск бессрочно. Автоматической ротации архивов, восстановления архива обратно в очередь и повторного применения отвергнутых событий нет. Для полного восстановления тома использовать согласованную копию остановленного relay, не заменять отдельный outbox старым файлом поверх работающего процесса. Потеря самого тома не исправляется протоколом; экспорт нужно хранить отдельно.

## Проверенный объём

- Rust: stale revision, частичный backup, ошибка записи snapshot после backup, restart/retry без удаления новых событий, заполнение карантина 4096 и восстановление admission после архива. Полный Rust workspace содержит 38 unit tests.
- Реальный Linux amd64 HBBR: экспорт, backup, повтор команды, права и аудит; 64 последовательные TCP-пары, 4 MiB проверенного payload за 1.62 с. При 60-секундном отключении control существующая data-пара продолжала передачу, затем HBBR/API перезапущены и очередь восстановлена.
- SQLite и PostgreSQL 17: миграции/reopen, изоляция, конкурентные повторы, ротация и уплотнение. 8 workers, 400 соединений, 1200 доставок включая 400 повторов, без потерь. SQLite: 4.03 с, p95 полного цикла 136.94 мс; PostgreSQL: 1.09 с, p95 26.11 мс.

Это измеренный локальный smoke, не производственный SLO, суточный soak или измерение максимума одновременных data-пар. Полная Pro-приёмка, multi-API, ARM64, официальный клиент и внешний TLS-стенд остаются открытыми. Результаты итоговых прогонов и ограничения — в [журнале](journal/2026-09-07.md).
