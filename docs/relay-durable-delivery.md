# REL-02: постоянная доставка lifecycle

Локальная разработка 2026-09-07. API и relay обновляются совместно; опубликованная 2.2.1 не содержит этого протокола. Публикации и production deployment по-прежнему запрещены.

## Relay

- WSS-режим использует `RDS_RELAY_OUTBOX_DIR`, по умолчанию `<RDS_DATA_DIR>/relay-outbox` (при отсутствии DATA_DIR — `/data/relay-outbox`). В отдельном dev-образе путь `/var/lib/relay-outbox`, отдельный Docker volume; UID 65532, остальная файловая система read-only.
- Snapshot `outbox.json` содержит UUID событий, состояния active/closed и активные пары. Паролей и credentials в нём нет. Запись: временный файл → fsync файла → rename → fsync каталога на Linux. Один процесс владеет каталогом через файловую блокировку. Не использовать один том одновременно для нескольких relay.
- Active сохраняется до начала передачи данных. Для каждой активной пары заранее резервируется место под closed. Максимум — 4096 событий вместе с резервами, файл до 2 MiB; две копии snapshot во время замены и служебные данные требуют дополнительного свободного места.
- При заполнении очереди новая пара не начинает передачу. При ошибке записи данные сохраняются в памяти, новые подключения блокируются до успешного flush; подтверждённый ранее snapshot остаётся основой восстановления. Повреждённый или несовместимый snapshot останавливает запуск, не удаляется автоматически.
- После перезапуска прежних TCP/WS-пар уже нет: для записанных active формируются closed. При обычном переподключении control-канала существующие data-пары продолжают работу, очередь сохраняется.
- Доставка последовательная: стабильный event UUID, новая transport session, повтор неподтверждённого события через 750 мс. Следующее событие проверяется с шагом 20 мс. Удаление из snapshot — после совпавшего ack; повтор после потери ack безопасен благодаря серверному receipt.
- Потеря диска/тома не исправляется протоколом. Если диск остаётся неисправным, очередь не считается доставленной. Не удалять том и snapshot для «исправления» ошибки; сначала сохранить и диагностировать данные.

## API

- Перед отправкой permit сохраняется `relay_authorizations`: UUID, relay ID, поколение credential, состояние и время создания. UUID не назначается другому узлу или повторно. Это авторизация lifecycle, а не восстановление разрешения на новый data-транспорт после restart.
- `relay_event_receipts` хранит event UUID, владельца, поколение и переход состояния. Receipt, монотонное состояние и проекция `connection_records` фиксируются одной транзакцией. Ack отправляется только после commit; повтор того же события возвращает подтверждение без повторной записи проекции.
- Проверяются действующий credential, enabled узла, принадлежность UUID и поколение ключа. Чужой relay, изменённый payload под прежним event ID и события прежнего поколения после ротации отклоняются. Поздний active не открывает уже закрытое соединение.
- Время в проекции относится к обработке события API; оно не является точной исторической отметкой момента обрыва при длительной недоступности.
- Лимит при выдаче — 100000 сохранённых authorizations на relay; на UUID допускается не более двух receipt-переходов. REL-OPS-01 добавляет ручное уплотнение завершённой истории старше 30 дней с сохранением защиты от replay; активные и неиспользованные permits не очищаются. См. [эксплуатационный контракт](relay-operations.md).
- Hello объявляет `durable=true`. Новый HBBR не подключается к gateway без этой возможности. Ранние локальные WSS-прототипы с непостоянными event ID нужно обновлять совместно с API.

## Эксплуатационные границы

Ротацию ключа желательно проводить после доставки очереди. При вынужденном отзыве безопасность имеет приоритет: неподтверждённые события старого поколения не принимаются новым ключом, события сохраняются в постоянный карантин и больше не задерживают следующие события. Карантин учитывается в общем лимите и не удаляется автоматически. Snapshot версии 2, миграция и ограничения описаны в [REL-OPS-01](relay-operations.md).

Постоянные receipts не делают gateway кластерным: маршрутизация команд между API-узлами ещё отсутствует. В этом блоке проверены Linux amd64, SQLite и локальный TLS; PostgreSQL runtime, ARM64, нагрузка и официальный клиент остаются открытыми.

## Проверки

- `TestDurableRelayDeliveryRestartIsolationAndRotation`: reopen SQLite, 8 конкурентных повторов, неизменность проекции, чужой relay, подмена payload, монотонное закрытие и ротация.
- Rust outbox tests: повтор стабильного event ID после restart, восстановление closed, ошибочный ack, единственный владелец, повреждённый файл, ошибка записи и восстановление, лимит с резервом закрытия.
- `TestRelayBinaryDurableRestart`: настоящий HBBR, разрыв control, завершение процесса, новый API/gateway без прежней памяти, перезапуск HBBR с тем же snapshot, закрытие прерванной пары, опустошение очереди и новая передача данных. Reopen БД проверяется отдельным store-тестом.
- `TestRelayBinaryWSS`: сохранены TLS/permit/terminate/TCP/WS/mixed/revoke сценарии.

Эти binary-тесты требуют `RDS_TEST_HBBR_BINARY`; без него SKIP. Результаты фактических прогонов — в [журнале](journal/2026-09-07.md), общие команды — в [testing.md](testing.md).
