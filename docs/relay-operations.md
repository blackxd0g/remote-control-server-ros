# REL-OPS-01: диагностика и обслуживание доставки

Реализовано локально 2026-09-07. Публикация и production deployment не выполнялись. Дополняет [durable delivery](relay-durable-delivery.md).

## Консоль и API

В разделе relay кнопка «Очередь и история» показывает ожидающие события, карантин, резервы закрытия, лимит, состояние записи на диск и старейшее ожидающее событие. Данные обновляются каждые 15 секунд; отключённый канал или снимок старше 20 секунд отображаются как неизвестное/устаревшее состояние. Отсутствие данных не означает пустую очередь.

GET `/api/admin/relay-servers/{relayID}/delivery` требует `relays.read`, POST `/api/admin/relay-servers/{relayID}/delivery/compact` — `relays.write`. Relay credential не предоставляет административный доступ. Runtime-снимок хранится только в памяти текущего gateway. Диагностический снимок содержит первые пять записей. REL-OPS-02 добавляет полный постраничный список, защищённый экспорт и архивирование с резервной копией: [обслуживание карантина](relay-quarantine-maintenance.md). Повторная отправка отвергнутых событий не реализована.

## Карантин

API возвращает `lifecycle_rejected` с причиной `credential_rotated` только действующему владельцу UUID при несовпадении поколения ключа. HBBR сохраняет такое событие в карантин и продолжает доставку следующих событий. Чужие UUID и прочие ошибки не превращаются в успешное подтверждение. Старое событие не применяется от имени нового поколения.

Snapshot автоматически мигрирует с версии 1 на 2, сохраняя event UUID. У старых событий время неизвестно (0). Прежний бинарник, поддерживающий только версию 1, не прочитает новый snapshot: перед обновлением сохранять резервную копию, для отката использовать совместимую версию и согласованную процедуру восстановления. Не удалять snapshot ради запуска.

Карантин входит в общий лимит 4096 вместе с ожидающими событиями и резервами. Он не задерживает голову очереди, но заполнение общего лимита блокирует новые пары. Автоматического удаления нет. При ошибке flush доставка повторяется после паузы, диагностика продолжает передаваться, новые пары не допускаются до восстановления записи. Для исследования snapshot работать с защищённой копией; идентификаторы соединений не публиковать в Markdown.

## Уплотнение истории

Администратор подтверждает ручную операцию: до 1000 завершённых UUID за один запрос, если receipt `closed` старше 30 дней. В одной транзакции сохраняется компактная запись владельца, поколения и event ID, после чего убираются подробные receipts и authorization. Записи соединений и аудит сохраняются. Действие записывается в обычный аудит приложения; аудит и транзакция уплотнения не являются одной атомарной операцией.

Компактные записи хранятся бессрочно: тот же UUID нельзя выдать повторно, точный поздний повтор подтверждается без изменения проекции, подмена отклоняется. Это уменьшение подробной истории, а не гарантированно ограниченный навсегда размер БД. Активные и неиспользованные разрешения не очищаются; их дальнейшая политика остаётся открытой. Автоматического расписания нет.

## Проверки и оставшиеся границы

Store-тесты проверяют поздний повтор, владельца, ротацию, сохранность проекции и границу 1000 + 1. Rust проверяет миграцию и сохранение карантина после restart. `TestRelayBinaryRotationQuarantine` запускает настоящий HBBR, смену ключа и API/gateway, проверяет карантин, диагностику и новую передачу данных. Для всех трёх binary-тестов нужен `RDS_TEST_HBBR_BINARY`, иначе они SKIP.

SQLite/Linux amd64 проверены локально. Проверка 1001 записи — регрессионный тест, не нагрузочный замер. Для исходного REL-OPS-01 PostgreSQL runtime и нагрузка не проверялись; результаты следующего блока приведены в REL-OPS-02. ARM64, официальный клиент, публичный TLS-стенд, multi-API и визуальная проверка браузера остаются открытыми. Фактические результаты — в [журнале](journal/2026-09-07.md).
